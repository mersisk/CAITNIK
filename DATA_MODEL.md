# DATA_MODEL.md

Публичная форма отправляет заявки в Node.js API на российском VDS. API сначала
сохраняет запись в PostgreSQL `artdeco`, затем пытается уведомить декоратора через
MAX. Корзина остаётся в `localStorage` только до успешного ответа API.

## Текущее решение: PostgreSQL и уведомление MAX

**Дата решения:** 6 сентября 2026 года.

- Endpoint: `POST /api/applications` на `https://api.artdeco-vl.ru`.
- Подключение к PostgreSQL берётся только из `process.env.DATABASE_URL`.
- Доступны два типа заказа: `catalog` и `custom`.
- Для `catalog` нужна минимум одна проверенная позиция каталога; сервер заменяет
  присланные название и цену каноническими значениями из `src/project.js`.
- Для `custom` корзина пуста, тип события равен «Индивидуальное оформление», а
  поле `wishes` обязательно.
- MAX вызывается только после успешного `INSERT`. Сбой MAX не удаляет запись и
  не превращает успешное сохранение в ошибку для клиента.
- `DATABASE_URL`, `MAX_BOT_TOKEN` и `MAX_CHAT_ID` существуют только в окружении
  backend. Секреты запрещено помещать во frontend, Git и Nginx-конфигурацию.
- Подробный запуск и проверка описаны в `docs/VPS_BACKEND.md`.

## Таблица `applications`

- `id` — идентификатор заявки, создаваемый PostgreSQL;
- `first_name`, `last_name`, `phone` — контакт клиента;
- `event_date`, `city`, `venue` — дата и место события;
- `messenger` — предпочитаемый канал связи;
- `event_type` — событие из каталога либо «Индивидуальное оформление»;
- `order_type` — только `catalog` или `custom`;
- `wishes` — пожелания, обязательные для индивидуального заказа;
- `cart_items` — JSONB-массив канонических позиций `{ id, name, price, quantity }`;
- `description` — дополнительное поле существующей таблицы, текущий API его не заполняет;
- `status`, `created_at` — состояние и время создания с серверными значениями по умолчанию.

## Универсальная запись

- `id` — уникальный идентификатор.
- `record_type` — тип: заявка, результат квиза, клиент или задача.
- `payload` — полезные поля конкретной записи.
- `status` — текущий этап.
- `created_at` — дата создания.
- `updated_at` — дата изменения.
- `archived_at` — дата архивации.

## Владелец данных

Production-заявки находятся в PostgreSQL на российском VDS. Публичный API умеет
только создавать заявку; чтение списка через публичный endpoint не добавляется.
Служебный экран старого starter-а не является интерфейсом production-таблицы.

## Не храним

- платёжные данные карты;
- пароли;
- паспортные данные;
- секретные ключи;
- лишние личные сведения «на будущее».

## История решения: данные заявки первой версии

**Дата решения:** 10 августа 2026 года.
**Статус:** интерфейс восстановлен решением от 5 сентября 2026 года; технические
и правовые замечания ниже остаются актуальны перед реальным запуском.

### Что выяснили

- Клиент передаёт выбранное оформление, имя, телефон, дату события, город,
  площадку и пожелания.
- Эти сведения нужны только для связи с клиентом и обработки его заявки.
- Открывать заявки на сайте с другого устройства или после закрытия браузера не
  требуется: владельцу достаточно получить их в Telegram.
- Заявки видит один владелец.
- Ожидаемая нагрузка — примерно 2–4 заявки в месяц.
- Имя, телефон и связанные с человеком сведения о событии являются персональными
  данными, даже если используются только для обратной связи.

### Что означают доступные режимы

**Локально** — сайт работает как демонстрация: данные остаются только в браузере
этого устройства и не попадают владельцу. В проекте не появляется сервер, база
или внешний сервис. Этот режим подходит для разработки и проверки с вымышленными
данными, но не для приёма настоящих заявок.

**Учебный Supabase** — заявки отправляются в учебную облачную базу. Для этого
понадобились бы таблицы, серверные настройки, правила доступа и управление
ключами. Продукту не нужен кабинет со списком заявок, а объём очень мал, поэтому
такая база добавит лишнее хранение и риски. Этот режим не выбираем для настоящих
данных клиентов.

**Реальный запуск в РФ** — публичная форма принимает данные настоящих клиентов.
Telegram в этом режиме служит уведомлением владельцу, а секрет бота находится
только на серверной стороне. До запуска потребуется определить законный и
безопасный маршрут данных, размещение первичной записи в России, срок хранения,
согласие клиента и политику обработки персональных данных. Это уже изменение
инфраструктуры, хотя интерфейс заявки может остаться прежним.

### Решение

1. Для текущей первой, локальной версии **достаточно памяти браузера; отдельная
   база данных не нужна**.
2. Учебный Supabase не подключаем: он не решает нужную владельцу задачу и создаёт
   ещё одно место с персональными данными.
3. Для публикации формы выбираем режим **«реальный запуск в РФ»**, но не запускаем
   передачу настоящих заявок только в Telegram без отдельной подготовки.
4. Перед реальным запуском нужно решить, где в России выполняется первичная
   запись персональных данных. Если действующие требования нельзя выполнить без
   хранения, понадобится минимальное российское хранилище, даже если владельцу
   не нужен отдельный экран заявок. Telegram тогда получает уведомление или
   разрешённую копию, а не является единственным основанием хранения.
5. На этом этапе внешние сервисы не подключаем; форму проверяем в локальном
   режиме на вымышленных данных.

### Что изменится перед реальным запуском

- форма будет обращаться к защищённому серверному обработчику, а не к Telegram
  прямо из браузера;
- токен Telegram-бота будет храниться в закрытых серверных настройках;
- будут передаваться только поля, необходимые для конкретной заявки;
- появятся политика обработки персональных данных и корректное основание для их
  обработки; отдельно проверяется необходимость уведомления Роскомнадзора;
- будут определены срок удаления заявок и порядок действий при ошибке отправки;
- до включения Telegram будет отдельно проверен вопрос передачи данных внешнему
  сервису и возможной трансграничной передачи.

### Новые риски выбранного пути

- **Правовой риск.** Форма делает владельца сайта оператором персональных данных;
  требования действуют независимо от небольшого числа заявок.
- **Риск размещения данных.** Обычные чаты Telegram являются облачными и хранятся
  на серверах Telegram; это нельзя автоматически считать российской первичной
  базой персональных данных.
- **Риск раскрытия секрета.** Если поместить токен бота в код страницы, его сможет
  увидеть посторонний и использовать для отправки сообщений от имени бота.
- **Риск доступа к заявкам.** Человек, получивший доступ к аккаунту или устройству
  владельца, сможет прочитать сведения клиентов.
- **Риск потери или дубля.** Telegram не заменяет журнал заявок: сообщение может
  не отправиться, быть удалено или повториться после сетевого сбоя.
- **Организационный риск.** Нужно вовремя удалять ненужные заявки и отвечать на
  запросы клиента о его данных.

### Основания для проверки перед публикацией

- [Федеральный закон № 152-ФЗ «О персональных данных»](https://ips.pravo.gov.ru/api/ips/legislation/document?baseid=None&hash=98490812b3409e2a8d78a11ca9010f434ea3d9250a11dbbdb78690cd5551bdd6)
  регулирует обработку персональных данных, конфиденциальность, обязанности
  оператора и локализацию данных при сборе через интернет.
- [Разъяснение Роскомнадзора для владельцев сайтов](https://82.rkn.gov.ru/directions/pers/p15375/)
  указывает, что сайт, собирающий сведения, по которым можно определить человека,
  является оператором персональных данных.
- [Политика конфиденциальности Telegram](https://www.telegram.org/privacy)
  объясняет, что обычные чаты являются облачными и их сообщения хранятся на
  серверах Telegram.

Эта карточка фиксирует техническое решение, но не заменяет юридическую проверку
конкретной схемы перед приёмом настоящих заявок.
